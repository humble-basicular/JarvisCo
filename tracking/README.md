# Proof-link tracking, preview funnel and offer v2

Independent Cloudflare Worker + D1 + Workers KV for the [preview funnel spec](../docs/SPEC-2026-10-preview-funnel.md) §§2–6; no CRM source changes. Deploy owner: parent/integration agent.

## Public endpoints

Both `jarvisweb.lt` and `www.jarvisweb.lt` have `/p/*` and `/t/*` Worker routes.

- `GET /p/a2345`: `302 Location: /rezultatai?r=a2345`, `Cache-Control: no-store`; records `click`. Exactly five lowercase characters from `23456789abcdefghjkmnpqrstuvwxyz`, with configured prefix `a` or `p`, are accepted. `a` targets `/rezultatai`; `GET /p/p2345` redirects to `/noriu?r=p2345`. Malformed/unknown-prefix paths redirect to `/` without an event. Codes are generated by CRM; Worker validates syntax/prefix, not existence in CRM (no lead registry here).
- `POST /t/e`: JSON `{ "code": "a2345", "type": "view" }`. Accepts `application/json`, `text/plain` (sendBeacon string), or an absent Content-Type; `application/json` Blob beacons also work. Seven public types: `view`, `scroll_proof`, `cta_sms`, `cta_call`, `pdf`, `arbcut`, `preview_cta`; callers cannot insert `click`. Successful insert: `204`; invalid JSON/code/type: `400`; unsupported media type: `415`; body over 1 KiB: `413`; rate-limited: `429` + `Retry-After`; unavailable storage: `503`.
- Public beacons use a shared D1 per-code fixed window (60 accepted events/minute across all beacon types and isolates). It is abuse mitigation, not identity verification: anyone knowing a code can fabricate a public beacon. Bot classification comes from request UA; no IP/full UA is stored. Legacy proof-code beacons accept no Origin header, the request URL’s own origin, or either first-party origin `https://jarvisweb.lt` / `https://www.jarvisweb.lt`; other origins are rejected (403). Site beacons have the exact-origin CORS policy below.
- Click logging/storage failure never changes the valid redirect. Invalid codes never store anything.

## Form submissions and attachments

`POST /t/form` accepts `multipart/form-data` following spec §4. Text is trimmed; unknown fields are ignored. For the original funnel, required `kind` is `preview_request` or `callback_request`; `code` is a configured five-character proof code or empty. `phone` is required without a code, otherwise optional: at most 20 characters, only digits/spaces/`+ - ( )`, and at least eight digits when supplied. Offer-v2 §2.4 adds two optional fields on both kinds: `email` (≤254 after trim, lower-cased, `^[^\s@]+@[^\s@]+\.[^\s@]+$`, else `400 field:"email"`) and `preview_via` (`sms`, `email` or empty, else `400 field:"preview_via"`). `preview_via=email` requires `email`. A homepage `preview_request` (no code) is accepted with a phone, or with an email unless `preview_via=sms`; `callback_request` still needs `code` or `phone`. Both are stored in the existing JSON payload (no migration); the feed emits `email` and `preview_via` (null when absent, also for rows stored before this change) on these two kinds only. Nothing is sent by email or SMS. Other optional fields:

| Fields | Validation |
|---|---|
| `name` | ≤80 characters |
| repeated `services`, repeated `area` | ≤12 entries each, ≤60 characters per entry; trimmed, blanks removed, deduplicated |
| `services_other`, `area_other` | ≤200 characters each |
| `photos_ok` | `yes`, `send_other`, or empty |
| `standout` | ≤1000 characters |
| `contact_time` | `morning`, `day`, `evening`, `sms`, or empty |
| repeated `files` | ≤8 files, each ≤10 MiB, total ≤25 MiB |

Files accept JPEG, PNG, WebP, HEIC, HEIF, GIF, PDF, Word `.doc/.docx`, Excel `.xls/.xlsx`, and plain-text MIME types exactly as in spec §4 (extensions alone do not authorize a type). Known scalar fields cannot repeat or contain a File; list entries must be text. Empty-string file entries and zero-byte nameless file inputs are ignored; non-empty string entries are rejected. A byte-counting TransformStream bounds multipart parsing to 25 MiB plus 64 KiB overhead even without Content-Length, avoiding a separate body/chunk concatenation. KV uploads use file streams. A populated `website` honeypot responds `200 {"ok":true}` with no storage, limiter claim or cleanup.

Success: `200 {"ok":true,"id":"<submission id>"}`. Errors: `400 {"error":"invalid","field":"<field>"}`, `413 {"error":"too_large"}`, `415 {"error":"file_type"}`, `429 {"error":"rate_limited"}` with `Retry-After`; storage failure returns `503 {"error":"unavailable"}`. Malformed/non-multipart requests identify `kind` as invalid. Forms have a separate atomic D1 budget: 5/minute per code and 10/minute for the anonymous no-code bucket, plus global UTC-day caps of 50 submissions and 300 MiB of files. Minute and daily claims share one transaction across isolates. Valid attempts reserve budget before KV writes; storage failures conservatively retain the claim. Daily denials return Retry-After until midnight UTC. Migration `0003_form_budgets.sql` is required. No IP, full UA, cookie or phone is stored in the limiter.

Submission IDs are UUID strings. KV keys are `s/<submission id>/<zero-based file index>`, with metadata `{name,type,size}` and `expirationTtl:31622400` (366 days). All KV writes finish before the event/submission D1 transaction publishes the entry. Names are stripped of control characters and `/`, capped at 100 Unicode code points, and default to `file` when empty; the same name is stored in KV metadata and D1 payload. On KV or D1 publication failure, the Worker attempts to delete only keys successfully written by that submission; cleanup failures fall back to TTL expiration. KV is eventually consistent, so a newly ingested file may briefly return 404 from another location ([Cloudflare KV write guidance](https://developers.cloudflare.com/kv/api/write-key-value-pairs/)). A failed submit is not automatically retried by the Worker.

`GET /t/files/<key>` requires the same Bearer token as `/t/events` (same digest comparison). It streams the KV bytes with stored `Content-Type`, `Content-Disposition: attachment`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. Missing/wrong credentials return 401; missing server secret returns 503; unknown keys return 404. Non-GET requests return 405.

## Offer v2 client sites and lead-gen

Implements [offer-v2 wire spec](../docs/SPEC-2026-10-offer-v2.md) §§1–2. `SITES` is a JSON-string Worker var, supplied in the private production config (test fixtures use synthetic origins):

```toml
[vars]
SITES = '{"arbcut":{"kind":"client","origins":["https://arbcut.lt","https://www.arbcut.lt"]},"sildymas-kaunas":{"kind":"leadgen","origins":["https://example-sildymas.lt"]}}'
```

Site codes match `^[a-z][a-z0-9-]{2,31}$`. Every entry requires kind `client` or `leadgen` and a nonempty array of exact HTTP(S) origins (`scheme://host[:port]`, no paths/trailing slash). Config is parsed once per config value per isolate; any malformed entry rejects the entire config safely with 503 on site requests, while legacy endpoints continue working. No registry, identities or origins are logged. **Adding a client site = edit `SITES` + deploy.** Preserve other existing private vars.

`POST /t/form` additionally accepts `site_inquiry` for client sites and `job_request` for lead-gen sites. Required fields: configured matching `site`, `phone` (same phone validation as the funnel), plus `consent=yes` for job requests. Optional trimmed scalar fields: `name` ≤80, `message` ≤2000, `service` ≤120, `location` ≤120, `contact_time` (same enum as the funnel); job requests also accept `brand` ≤60. `code` is ignored; client inquiries also ignore `brand` and `consent`. File validation, storage, receipt IDs and honeypot rules are shared. Site/Origin authorization precedes the honeypot; accepted traps publish nothing and consume no budget. Unknown/wrong-kind site returns 400 `{error:"invalid",field:"site"}`; missing/foreign Origin returns 403 `{error:"origin"}`.

Allowed origins receive `Access-Control-Allow-Origin: <origin>` and `Vary: Origin`, including validation/rate/storage errors. `OPTIONS /t/form` and `/t/e` allow POST with Accept/Content-Type headers from configured origins only. Preflight has no site field, so it checks the union of configured origins; the actual POST verifies the specific site's origin. Original funnel kinds use the same legacy Origin policy as proof-code beacons: no header, the request URL’s own origin, or either `https://jarvisweb.lt` / `https://www.jarvisweb.lt`. This permits apex/www cross-host posts; other origins return 403. No wildcard CORS.

Site forms with `Accept` containing `application/json` receive existing JSON responses. Other Accept values (including missing) receive 303 to `<Origin>/aciu` on success, `<Origin>/aciu?klaida=1` on errors, with Retry-After retained when rate limited. **Safety interpretation for lead review:** unconfigured/missing origins receive JSON denial rather than redirecting to an untrusted destination; malformed forms from a configured external origin use the error redirect. This prevents an open redirect. No-JS behavior of original funnel forms stays unchanged.

Site budgets use atomic D1 transactions: 5 forms/minute and 30/UTC day per site, 100 forms and 300 file writes/UTC day across all sites. Zero-file forms remain available at the file-write cap. Claims precede KV writes and remain spent after storage failure. These budgets are separate from the existing 50/day and 300 MiB/day funnel budgets in both directions. `site_daily_budgets` records only site code, UTC day, submission count and file-write count; minute buckets use `site-form:` and `site-beacon:` prefixes. No IP, full UA, cookie or phone is stored in budgets. Prior-day site budgets are included in existing request-time retention cleanup.

`POST /t/e` also accepts text/plain sendBeacon JSON `{site:"arbcut",type:"cta_call"}` or `cta_sms`. `site` and `code` must not both be present (even null); site beacons require the same configured exact Origin and share 60/minute per site across both types. They do not consume form budgets. Site events carry `code:null` and the site code, and site beacons have no submission. Site form submissions carry exactly `name`, `phone`, `message`, `service`, `location`, `brand`, `contact_time`, `consent`, `files`; empty text becomes null, consent is boolean (client inquiries false), and files keep `{key,name,type,size}`. The feed envelope/cursor and file endpoint are unchanged.

### Inquiry tracking beacons (migration `0005_site_beacons.sql`)

`POST /t/e` for a site now also accepts `form_open` and `form_submit` next to `cta_call`/`cta_sms`. Optional anonymous context, all or nothing: `page` (path, no query/fragment/space, ≤120), `loc` (the button's `data-loc`, `[a-z0-9_-]{1,40}`, else null), `ref` (`direct|search|social|internal|other`), `mobile` (boolean). A malformed context is dropped (the event still counts). The feed adds `meta:{page,loc,ref,mobile}` to those events only; time is the D1 `at`. No cookie, IP, full UA or visitor id is stored. Form submits to `/t/form` stay `site_inquiry`; the snippet skips forms that post there so nothing is counted twice. Deploy order: CRM first (it must accept `form_*` and `meta`), then apply `0005`, then the Worker. Never roll the CRM back below the contracts commit "site beacons form_open/form_submit" once the Worker is deployed (one such row makes an old CRM's strict page parse fail and stalls real `site_inquiry` rows too); if the CRM must roll back, roll the Worker back first. `SITES.<code>.origins` must list every production origin exactly (apex and `www`); a preview origin gets 403.

**Deploy the CRM parser/contracts before this Worker**: the old CRM rejects the new event types and `site` field. ## CRM pull endpoint and cursor (coordinate before CRM implementation)

`GET /t/events?since=<ISO>&limit=500` requires `Authorization: Bearer <EVENTS_TOKEN>` (Worker secret). Missing/wrong credentials: `401`; missing server secret: `503`. `since` is required and must include a UTC offset or `Z`; it is normalized to UTC milliseconds. `limit` defaults to 500, integer 1–500. Invalid query/cursor: `400`. All responses are uncached.

```json
{
  "events": [
    { "id": "42", "code": "a2345", "site": null, "type": "click", "at": "2026-10-11T13:00:00.000Z", "ua_class": "human" }
  ],
  "next_cursor": null,
  "has_more": false
}
```

Feed IDs are persistent SQLite AUTOINCREMENT IDs encoded as decimal strings, shared by beacons, clicks and submissions. They are distinct from the UUID submission receipt/KV ID. Migration `0002_submissions.sql` preserves existing IDs and the AUTOINCREMENT high-water mark even when older rows have expired.

The feed adds `preview_cta`, `preview_request`, and `callback_request`. Only the two form types may have `code:null` (homepage). Form entries carry `submission` with exactly `name`, `phone`, `email`, `preview_via`, `services`, `services_other`, `area`, `area_other`, `photos_ok`, `standout`, `contact_time`, and `files`; optional empty text becomes null and missing lists stay `[]`. `files` contains `{key,name,type,size}` objects. Normal beacons/clicks do not carry `submission`. Every event includes `site:null` unless it belongs to an offer-v2 site. The envelope and cursor version remain unchanged.

Deduplicate by `(Worker database identity, id)`; never deduplicate on timestamps, which can be equal. Events are sorted ascending by `(at, id)` and initial `since` is **inclusive**.

When `has_more` is true, call with the **same `since`** and `cursor=<next_cursor>` (URL-encode it). The opaque versioned cursor contains a snapshot high-water ID and last `(at,id)`, preventing gaps at equal timestamps and preventing new arrivals from extending an in-progress page set. `next_cursor` is non-null only when another page exists. Commit each page's events and checkpoint together in CRM; retrying a page returns the same retained event IDs. A cursor is a paging token, not an authorization token.

After `has_more:false`, start the next poll with `since` equal to the largest ingested `at`, no cursor; boundary events are replayed and must be deduplicated by ID. Preserve the previous `since` on an empty pull. Late-arriving events inserted during paging are included on that next poll. Persist a page cursor only for unfinished paging. Never advance `since` to the pull request's wall-clock time: that could skip concurrent inserts. Persist nothing past a failed page. Timestamps are generated by D1, not supplied by public callers.

`ua_class` is `bot` for facebookexternalhit, WhatsApp, TelegramBot, Slackbot, Twitterbot, SkypeUriPreview, Googlebot, bingbot, Google-PageRenderer, or generic `bot|crawler|spider|preview` (case-insensitive), else `human`. A `click` alone is not a confirmed real view; CRM should mark proof viewed on a `view` beacon and retain the classifier.

## Retention and operations

Events and submissions expire after 12 calendar months in UTC (month-end clamps to the last day of the destination month). Request-time cleanup deletes expired submissions, events, minute rate-limit buckets and prior-day form budgets, at most once per hour using a D1 lease. Pulls always exclude expired events and submissions even before deletion. No cron/scheduler is configured; physical deletion awaits the next handled request after expiry if the Worker is idle. Secrets, IPs, and full user agents are never logged or committed.

Local commands and deployment prerequisites are documented below. No provisioning or deployment is performed by this child.

## Deployment prerequisites — parent only

The production Worker already has private D1, token and zone-route configuration. Preserve it and use the preview-funnel steps below. For a fresh installation, provision D1 and set `EVENTS_TOKEN` privately before enabling routes; never replace repository placeholder IDs with real ones. Keep both apex/www DNS records proxied and retain the Vercel origin. Four configured routes cover apex/www `/p/*` and `/t/*`; `workers.dev` and preview URLs are disabled. `npm run deploy:check` only validates bundling/configuration.

`[observability].enabled=false`, no `console` calls and `send_metrics=false` keep application request logs and Wrangler telemetry disabled in this configuration. Cloudflare infrastructure may independently retain provider-level request metadata; this Worker stores only the schema documented above. Request-time cleanup avoids creating any persistent automation; if strict physical deletion during completely idle periods is later required, the parent must explicitly approve a built-in cron change before enabling it.

For implementation reference: [D1 transactional batches](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), [Miniflare D1 access](https://developers.cloudflare.com/workers/testing/miniflare/storage/d1/). Live Cloudflare routes, live D1, Vercel interactions, site/CRM beacon integration and production retention have not been tested by this child.
