# Proof-link tracking contract v1

Independent Cloudflare Worker + D1 for spec §4; no CRM source changes. Deploy owner: parent/integration agent. This contract is committed before implementation so the site and CRM can implement against it.

## Public endpoints

Both `jarvisweb.lt` and `www.jarvisweb.lt` have `/p/*` and `/t/*` Worker routes.

- `GET /p/a2345`: `302 Location: /rezultatai?r=a2345`, `Cache-Control: no-store`; records `click`. Exactly five lowercase characters from `23456789abcdefghjkmnpqrstuvwxyz`, with configured prefix `a`, are accepted. All configured prefixes target `/rezultatai`; keep that target when adding future prefixes. Malformed/unknown-prefix paths redirect to `/` without an event. Codes are generated by CRM; Worker validates syntax/prefix, not existence in CRM (no lead registry here).
- `POST /t/e`: JSON `{ "code": "a2345", "type": "view" }`. Accepts `application/json`, `text/plain` (sendBeacon string), or an absent Content-Type; `application/json` Blob beacons also work. Six public types: `view`, `scroll_proof`, `cta_sms`, `cta_call`, `pdf`, `arbcut`; callers cannot insert `click`. Successful insert: `204`; invalid JSON/code/type: `400`; unsupported media type: `415`; body over 1 KiB: `413`; rate-limited: `429` + `Retry-After`; unavailable storage: `503`.
- Public beacons use a shared D1 per-code fixed window (60 accepted events/minute across all six types and all isolates). It is abuse mitigation, not identity verification: anyone knowing a code can fabricate a public beacon. Bot classification comes from request UA; no IP/full UA is stored. Same-origin beacons; no permissive CORS.
- Click logging/storage failure never changes the valid redirect. Invalid codes never store anything.

## CRM pull endpoint and cursor (coordinate before CRM implementation)

`GET /t/events?since=<ISO>&limit=500` requires `Authorization: Bearer <EVENTS_TOKEN>` (Worker secret). Missing/wrong credentials: `401`; missing server secret: `503`. `since` is required and must include a UTC offset or `Z`; it is normalized to UTC milliseconds. `limit` defaults to 500, integer 1–500. Invalid query/cursor: `400`. All responses are uncached.

```json
{
  "events": [
    { "id": "42", "code": "a2345", "type": "click", "at": "2026-10-11T13:00:00.000Z", "ua_class": "human" }
  ],
  "next_cursor": null,
  "has_more": false
}
```

IDs are persistent SQLite AUTOINCREMENT IDs encoded as decimal strings. Deduplicate by `(Worker database identity, id)`; never deduplicate on timestamps, which can be equal. Events are sorted ascending by `(at, id)` and initial `since` is **inclusive**.

When `has_more` is true, call with the **same `since`** and `cursor=<next_cursor>` (URL-encode it). The opaque versioned cursor contains a snapshot high-water ID and last `(at,id)`, preventing gaps at equal timestamps and preventing new arrivals from extending an in-progress page set. `next_cursor` is non-null only when another page exists. Commit each page's events and checkpoint together in CRM; retrying a page returns the same retained event IDs. A cursor is a paging token, not an authorization token.

After `has_more:false`, start the next poll with `since` equal to the largest ingested `at`, no cursor; boundary events are replayed and must be deduplicated by ID. Preserve the previous `since` on an empty pull. Late-arriving events inserted during paging are included on that next poll. Persist a page cursor only for unfinished paging. Never advance `since` to the pull request's wall-clock time: that could skip concurrent inserts. Persist nothing past a failed page. Timestamps are generated by D1, not supplied by public callers.

`ua_class` is `bot` for facebookexternalhit, WhatsApp, TelegramBot, Slackbot, Twitterbot, SkypeUriPreview, Googlebot, bingbot, Google-PageRenderer, or generic `bot|crawler|spider|preview` (case-insensitive), else `human`. A `click` alone is not a confirmed real view; CRM should mark proof viewed on a `view` beacon and retain the classifier.

## Retention and operations

Events expire after 12 calendar months in UTC (month-end clamps to the last day of the destination month). Request-time cleanup deletes expired events and expired rate-limit buckets, at most once per hour using a D1 lease. Pulls always exclude expired events even before deletion. No cron/scheduler is configured; physical deletion awaits the next handled request after expiry if the Worker is idle. Secrets, IPs, and full user agents are never logged or committed.

Local commands and deployment prerequisites are documented below. No provisioning or deployment is performed by this child.

## Local commands (run inside tracking)

```sh
export PATH=/opt/homebrew/bin:$PATH
npm ci
npm test
npm run typecheck
npm run migrate:local
npm run dev
npm run deploy:check
```

Keep `.dev.vars` local/ignored with a test `EVENTS_TOKEN` for `wrangler dev`. Tests use an ephemeral local D1, fake token, workerd HTTP requests and two isolates sharing a D1 for limiter concurrency. The test wrapper drains background writes for deterministic SQL assertions; a separate handler test checks that slow/failed storage cannot delay redirects. Tests do not contact the live site, send SMS, submit forms, provision resources, or make paid API calls. Dependencies and lockfile live only in `tracking/`; no root site dependency changes. Installed Wrangler 4.149.0 uses Miniflare `5.20261006.1-alpha`; the tests pin that same runtime and its supported v4 option converter.

## Deployment prerequisites — parent only

1. Ensure the Cloudflare account/zone has Workers and D1 on the free plan and that both apex/www DNS records are proxied; retain the Vercel origin. Authenticate Wrangler locally (do not write account tokens into the repo).
2. Create a free D1 database named `jarvisweb-proof-events`; replace the all-zero placeholder `database_id` in `wrangler.toml` with its actual ID. No database exists from this implementation task.
3. Apply `npx wrangler d1 migrations apply DB --remote` **before** enabling the routes. The migration creates only the new tracking schema; it does not touch CRM data. Review/backup any already-existing database before reuse.
4. Set a fresh random `EVENTS_TOKEN` with `npx wrangler secret put EVENTS_TOKEN`; provide the same token privately to the separate CRM integration. Never log/commit the value. Configure CRM exactly as the inclusive-since/cursor contract above.
5. After parent obtains the required preview approval, run `npx wrangler deploy` from `tracking/`. Four configured zone routes cover apex/www `/p/*` and `/t/*`; `workers.dev` and preview URLs are disabled. `npm run deploy:check` is bundle/config validation only, **not a deployment**.
6. Verify a parent-approved synthetic code redirects and records human/bot clicks; post only synthetic tracking events and pull them with the secret. Check both hosts, beacon types, auth denial, and CRM ingestion. Do not submit a real inquiry or send SMS.

`[observability].enabled=false`, no `console` calls and `send_metrics=false` keep application request logs and Wrangler telemetry disabled in this configuration. Cloudflare infrastructure may independently retain provider-level request metadata; this Worker stores only the schema documented above. Request-time cleanup avoids creating any persistent automation; if strict physical deletion during completely idle periods is later required, the parent must explicitly approve a built-in cron change before enabling it.

For implementation reference: [D1 transactional batches](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), [Miniflare D1 access](https://developers.cloudflare.com/workers/testing/miniflare/storage/d1/). Live Cloudflare routes, live D1, Vercel interactions, site/CRM beacon integration and production retention have not been tested by this child.
